# Phase 1 benchmark protocol (predeclared)

Benchmark ID LF-B01. This is authored-project validation, not a gameplay/simulation benchmark. Use the locked release workspace. Workload derives from the original Lantern project; retain one role and one trial and generate N unique recruits with identical valid values and shared role reference. Generic rank-limit predicate runs once per recruit. N = 100, 1,000, 10,000. Record normalized UTF-8 byte length, 7 repeated runs after one warm-up for each operation, median elapsed microseconds for (1) validate already decoded object, (2) strict decode + validate, (3) normalization of already decoded object (includes validation). Verify every operation succeeds; normalization deterministic output outside timed measurement. Single-threaded, no IO timed, no external network, no interactive UI. Rust release and locked dependency versions, CPU/OS/memory recorded with results; hosted runners variable, comparisons only with same workload/build and comparable environment. No elapsed-time pass/fail threshold until baseline measured. Expected correctness: all cases accepted and round-trip stable; malformed overbudget fixture separately rejected by regression suite. Reject result if any case fails. Report median and per-run raw values, not fastest run or unsupported hardware estimates.

Phase 2 future LF-B02 encounter workload: Lantern attempt with fixed initial state, parameterized uniform integer receipt and rank; 100,000 independent trials reset state each time; use semantically aligned recorded draws or versioned seeded streams; verify exact 11/20 success probability in a separate 20-case enumeration and exactly one focus spent per valid attempt. Record success count, error/reject dispositions, trace validity, elapsed time, peak memory, release build and hardware. 100,000 trials is workload size, not guaranteed speed. First compare serial correctness; parallel gate in Phase 5. No claim of throughput or confidence until measured. For diceless Council, replay scenario includes threshold guard, eligible approval, cancel, stale receipt, and competing pending requests; compare canonical resulting snapshots and ordered event receipts; no randomness.

Existing prototypes are isolated feasibility evidence. Benchmark source and real measurement must be recorded separately from this preregistration.
